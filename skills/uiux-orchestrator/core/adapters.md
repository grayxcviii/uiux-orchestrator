# Bounded skill adapters

An adapter is a scoped use of an existing skill, defined by this orchestrator. It is not a new
upstream command or another full driver. Only registry `specialist_slots` authorize this mode;
other driver entries cannot acquire a specialist role by changing their label.

## frontend-design: `design-reasoning`

Use for a compatible web surface's concept stage, after foundation and before final art direction.
Also use for creative refinement/Refresh inside an existing system: inspected product context,
current UI and fixed tokens provide its foundation. The adapter explores the requested component
or surface within those constraints; it does not become a full driver or replace the brand.
Check availability/platform as usual. Load the actual frontend-design SKILL.md and execute its
planning and review-against-brief work. The user-approved bounded task stops before code/build;
do not edit upstream instructions or pretend to run an upstream `design-reasoning` command.

**Input:** original brief, inspected product/platform context, foundation evidence and UX plan,
brand constraints, available content/assets, success criteria and explicit dislikes.

**Work and output:**

1. Develop meaningfully different experience concepts: narrative, hierarchy, primary action,
   content structure, layout sketches and interaction opportunities grounded in the subject.
2. Evaluate the alternatives against the brief and explain the chosen concept. If the user
   delegated decisions, choose and continue; otherwise follow the requested exploration gate.
3. Return a concept brief with alternatives, rationale, constraints, provisional visual ideas and
   what the art-direction stage must preserve. Apply the skill's specificity/self-critique work.

Palette/font/token sketches from frontend-design remain suggestions at this stage. Do not create
production UI, copy a kit, mutate project tokens, select the final visual system or overrule the
later art-direction owner. Record `mode: design-reasoning` on the real activation receipt and
link its accepted output only to `design-reasoning` coverage using `source: skill`.

In scoped refinement, the next visual owner is a compatible specialist such as Impeccable tone,
typeset or layout, with the existing system as its constraints. No full driver is required to
execute creative reasoning. Carry the chosen alternative and intended benefit into before/after
review; keep the same receipts and accepted-handoff requirements as other orchestrated work.

## Coexistence with Taste or another driver

Select one full visual driver using the normal table. On a suitable marketing/product site this
is Taste. The concept adapter passes the chosen experience brief to it; Taste executes its own
planning/deal/visual process and authors the final art direction. Any exploratory token choices
from foundation/concept are reconciled now, not silently locked before Taste works.

After that direction is accepted, finalize the actual design system. Reconcile tokens, type,
components and responsive/motion conventions with the foundation's constraints and the final
visual direction. Foundation data informs this work; it does not override the accepted visuals.
If the visual driver discovers a genuine concept/brief defect, return it to the concept owner
with evidence, revise the affected handoff and revalidate dependent outputs.

When frontend-design itself is selected as the sole full driver, its full pipeline may cover
both concept reasoning and art direction with distinct accepted stage outputs. Do not invoke a
second full pipeline on the same surface merely to fill another name in the diagram.

## Platform and failure boundaries

This frontend adapter is web-only. Native/RN/Flutter use compatible concept expertise (e.g.
Impeccable shape) and platform guidance; a fixed stage does not mandate a web-only provider.
If bounded execution is unsupported by the actual installed skill or its hard prerequisites,
record that result and route the next compatible concept specialist. Do not silently use a full
second driver or describe an unexecuted adapter as completed.

Adapters do not weaken execution receipts, accepted handoffs, permissions, accessibility floors,
review independence or the fallback/status rules in [orchestration.md](orchestration.md).
